which is free software under the GNU General Public License version 3. Section
5 of that licence asks a modified work to say prominently that it was changed,
and when. This file is that notice.

Upstream's copyright and licence are unchanged and remain in place. "Omnuv" is
our own name and mark; the upstream project does not endorse this build.

| 2026-09-15 | `14c26d8c` | A segue of our own, `app/omnuv/OmnuvSegue.qml`, beside upstream's rather than instead of it: the same seven `Session` signals, a five-rung ladder in place of one spinner, and a failure that is a sentence about what actually broke, the actions that apply to it, and the stage name and numeric code folded away under *Details*. Upstream's `Starting %1 failed: Error %2` dialog is never opened from our path, and the build fails if anything under `app/omnuv/` reaches for it. The sentences are keyed on moonlight-common-c's own stage names and the build also fails when one of them has no sentence. A separate file rather than an edit to `app/gui/StreamSegue.qml`, which `CliQuitStreamSegue` and upstream's application grid push and expect to behave as it always has, and which the budget check pins as the one place upstream's numeric-code dialog is referenced from. | 2026-09-15 | `14c26d8c` | A pairing nobody types. On Play against an unpaired machine the client still mints Moonlight's four-digit PIN, but it now hands it to the machine's own streaming host over the private network — using the single-use web login that machine minted for itself and published through Omnuv — and the person sees the machine become ready without reading a number off one screen and typing it into another. The PIN dialog survives as the fallback it now is: it opens only when the delivery failed, says which step failed in a sentence, and folds the status code away under *Technical detail*. New code is `app/omnuv/pairing.(h\|cpp)` plus the two calls in `app/omnuv/omnuvsession.cpp`; the credential is never written to a log, a setting or the credential store, and the build fails if a path from one to either appears. Also fixes a live defect: `ComputerModel::pairingCompleted` was never connected in this view, so until today an Omnuv pairing that failed said nothing and one that succeeded left its dialog on screen. |
| 2026-09-15 | `14c26d8c` | Machines are cards rather than list rows: Core's status word with a dot beside it, what the provider last observed and when — or nothing, when it did not observe — the launch ladder while a machine is starting, one primary action and a menu. `app/omnuv/MachineCard.qml`, with the extra fields the buyer API already sent and the client was dropping (`private_ip`, `last_error`, the `operation` and `observation` objects) read in `app/omnuv/machinemodel.(h\|cpp)`. The ladder's four steps, the field each is confirmed by, and the five states a step can be in are the web console's, and the build fails if they drift apart. |
| 2026-09-15 | `14c26d8c` | `app/omnuv/StreamSettingsSheet.qml`: the six settings a gaming buyer changes — a preset, resolution and frame rate, bitrate, display mode, frame pacing, audio — bound straight to upstream's `StreamingPreferences` with no copy of our own, and *Advanced* pushing upstream's own page for the other nine hundred lines. |
| 2026-09-15 | `14c26d8c` | `Theme` gains the 4px spacing grid and the six colours a card needs that a style cannot draw: Microsoft's own `CardBackgroundFillColorDefault`, `CardStrokeColorDefault` and the four `SystemFillColor*`, light and dark, transcribed from `microsoft/microsoft-ui-xaml`. Everything the style can colour is still the style's. |
| 2026-09-15 | `14c26d8c` | `Moonlight.exe stream <machine> "<app>"` opens our segue instead of upstream's. Measured on the Windows rig rather than reasoned about: that command answered a failed stream with upstream's Material dialog and upstream's words, and it is the command `omnuv-connect --stream` runs, the command every `omnuv://stream` link from the console runs, and the command the gaming-rig end-to-end streams with — so it was the buyer-facing surface for everyone outside the widget, and the automated proof of streaming was exercising a screen no buyer is meant to see. `app/omnuv/OmnuvCliSegue.qml` is that verb's initial view now: the same segue, with `CliStartStream::Launcher` attached, so the thirty seconds before a `Session` exists light the same ladder and the launcher's own failures are rendered as sentences with its message folded under *Details*. Three lines in `app/main.cpp`, in the arm that already builds that launcher, because the switch that chooses an initial view is there and so is the parse that produces the two positional arguments. `quit` and `pair` are untouched and still upstream's. |
| 2026-09-15 | `14c26d8c` | The segue reports the sentence it rendered, at Info level, on one line: `Omnuv segue: failed headline=` and `Omnuv segue: details=`. The lab's Windows play had been reading those two lines since it was written and nothing had ever emitted them, so a failure panel that drew perfectly and one that drew nothing were the same fact to anything that could not look at the screen. It reports text and grades nothing — whether what was drawn was a sentence, and whether it carried a number, are judged by the harness, out of the client's reach. |
| 2026-09-15 | `14c26d8c` | In the stream: a quality mark, a stats panel and a state for a picture that has stopped. Upstream computes ten statistics once a second and presents them as ten lines of yellow text on a hotkey; the same numbers now also decide a four-bar mark that draws only when something is wrong and names it in two words, and the ten lines are grouped *Video · Network · Host* with the two readings that can be unknown saying so rather than showing a zero. Everything that decides is `app/omnuv/streamquality.(h\|cpp)`; the four thresholds are relative to the negotiated frame rate and the frame interval rather than absolute, each carries the reason it is that number, and all eleven can be moved on the hardware with `OMNUV_STREAM_QUALITY=name=value,…` without a rebuild. None of it is QML: `app/streaming/session.cpp` suspends Qt for the whole of a stream, so what draws is upstream's own overlay, in the slot it already has, in the font it already has — which is why the bars are ASCII. |
| 2026-09-15 | `14c26d8c` | A stream whose picture has stopped says so instead of freezing. Nothing reconnects that did not already: the transport retries for ten seconds before it gives up, and until today nobody drew anything during them — the last frame simply sat there, and then a dialog said `Error code: -1`. The overlay now says which machine it is waiting for, for how long, and how to stop waiting; it lifts by itself when frames come back; and when the stream really is over, the sentence says the picture stopped arriving rather than naming a number. Four call sites in `app/streaming/session.cpp` and one in `app/streaming/video/ffmpeg.cpp`, each of which is the only place the thing it needs exists. |
| 2026-09-15 | `14c26d8c` | One line a second of stream statistics to the log file, whether or not the overlay is on. `scripts/gaming-rig-e2e` samples the stream at 10, 30 and 60 seconds through the hypervisor's guest agent, which can read a file and cannot see a pixel; before this the numbers were written once, at decoder teardown, as a whole-session average that cannot answer "over the last 30 seconds". An unknown reading is written `na` rather than `0`, because a zero is a pass. |
| 2026-09-15 | `14c26d8c` | `OverlayManager` gains a colour setter beside the getter it already had, so the in-stream mark can be amber at one threshold and red at another. The alternative was a third overlay type, whose position is hard-coded in all six video renderers. |

| 2026-09-15 | `14c26d8c` | The tray becomes the widget it was standing in for. New files are `app/omnuv/traystate.h` (no Qt in it, so its exit check runs in CI in a second), `app/omnuv/traystate_check.cpp` and `app/omnuv/probe.(h\|cpp)`; `app/app.pro` gains them and `-lshell32`.
